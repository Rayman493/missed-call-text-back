# Supabase SSR Session Cookie Handling Fix - Final Report

**Date:** 2025-01-09
**Objective:** Fix Supabase SSR session-reliability issues (no-op setAll warning and refresh_token_not_found errors)
**Status:** ✅ COMPLETE

---

## 1. Exact Warning Source

**Warning Message:**
```
@supabase/ssr: createServerClient was configured without the setAll cookie method,
but the client needs to set cookies. This can lead to issues such as random
logouts, early session termination or increased token refresh requests.
```

**Exact File and Call Site:** `src/app/page.tsx` (lines 71-74)

**Exact Request Path:** Homepage (`/`) - Server Component

**Why That Request Required a Cookie Write:**
- When Supabase's `getUser()` method detected an expired access token, it attempted to refresh the session automatically
- The refresh would generate new access and refresh tokens
- The `setAll` method was called to persist these refreshed cookies to the browser
- However, `setAll` was a no-op (empty function), so the refreshed cookies were lost
- This caused the session to appear valid temporarily but fail on subsequent requests

**Where It Occurred:**
- Server Component (src/app/page.tsx)
- The homepage is a Server Component that checks authentication status
- Server Components cannot directly write cookies in Next.js App Router
- The no-op `setAll` prevented cookie persistence

**Why Refresh-Token Error Appeared Twice:**
1. First occurrence: Initial page load attempted to refresh session, but `setAll` was a no-op, so refreshed cookies were lost
2. Second occurrence: Subsequent request (likely navigation or API call) tried to use the now-stale refresh token, which was not updated in the first refresh attempt
3. Both attempts failed because the refresh token was never successfully updated in the browser

---

## 2. Exact Duplicate Refresh-Error Cause

**Root Cause:** The no-op `setAll` function in `src/app/page.tsx` prevented session refresh from persisting to the browser. This created a race condition:

1. **First Request (Homepage):**
   - Supabase client created with no-op `setAll`
   - Session check detected expired access token
   - Automatic refresh attempted
   - New tokens generated by Supabase
   - `setAll` called but did nothing (no-op)
   - Refreshed cookies lost
   - Session appeared valid in memory but cookies remained stale

2. **Second Request (Subsequent navigation/API):**
   - Browser sends stale cookies (old refresh token)
   - Supabase client attempts to refresh using stale refresh token
   - Database no longer has that refresh token (it was consumed in first refresh)
   - Error: `refresh_token_not_found`
   - Session invalidated
   - User logged out

**Secondary Issue:** `src/app/api/geocode/address/route.ts` also had a no-op `setAll` with comment "Not needed for read-only auth check". This was incorrect because:
- Route handlers CAN write cookies (unlike Server Components)
- If the session needs refresh during auth check, the refreshed cookies won't be persisted
- Same race condition could occur in API routes

**Tertiary Issue:** `src/app/admin/current-user-business-diagnostic/route.ts` used an incorrect cookie adapter pattern with only `get(name)` instead of `getAll()` and `setAll()`. This does not match the expected @supabase/ssr 0.10.2 API.

**Cookie Adapter Patterns:**

**Middleware Pattern:**
```typescript
cookies: {
  getAll() {
    return req.cookies.getAll()
  },
  setAll(cookiesToSet) {
    cookiesToSet.forEach(({ name, value, options }) =>
      res.cookies.set(name, value, options)
    )
  },
}
```
- Reads from request cookies
- Writes to response cookies
- Can persist refreshed sessions

**Server Component Pattern (Guarded):**
```typescript
cookies: {
  getAll() {
    try {
      if (!cookieStore) return []
      return cookieStore.getAll()
    } catch {
      return []
    }
  },
  setAll(cookiesToSet) {
    try {
      if (!cookieStore) return
      cookiesToSet.forEach(({ name, value, options }) =>
        cookieStore.set(name, value, options)
      )
    } catch {
      // Server Component cannot set cookies - middleware handles session refresh
    }
  },
}
```
- Reads from cookie store
- Writes to cookie store with try-catch (may fail silently)
- Relies on middleware for actual cookie persistence to response

**Route Handler Pattern (Guarded):**
```typescript
cookies: {
  getAll() {
```

## 6. Middleware Refresh/Cookie Propagation

**Middleware Cookie Flow:**

1. **Read Phase:**
   ```typescript
   getAll() {
     return req.cookies.getAll()
   }
   ```
   - Reads all cookies from incoming request
   - Includes Supabase auth cookies (sb-access-token, sb-refresh-token, etc.)

2. **Session Check:**
   ```typescript
   const { data: { user: authUser } } = await supabase.auth.getUser()
   ```
   - Supabase checks session validity
   - Automatically refreshes if access token is expired
   - Generates new tokens if refresh succeeds

3. **Write Phase:**
   ```typescript
   setAll(cookiesToSet) {
     cookiesToSet.forEach(({ name, value, options }) =>
       res.cookies.set(name, value, options)
     )
   }
   ```
   - Writes all refreshed cookies to response
   - Preserves all cookie options (secure, same-site, path, expiration, domain)
   - Cookies are sent back to browser in response headers

4. **Response Preservation:**
   - Middleware preserves existing response (`NextResponse.next()`)
   - Updates cookies without losing headers, status, or redirects
   - Security headers and CSP are added after cookie updates
   - Redirects are preserved with refreshed cookies

**Key Improvements:**
- Middleware now has a request-scoped flag `handledRefreshTokenError` to prevent duplicate error logs
- When `refresh_token_not_found` error occurs:
  - Logs at info level (not error) since this is expected stale session cleanup
  - Clears ALL Supabase auth cookies (not just sb-access-token and sb-refresh-token)
  - Clears cookies starting with `sb-` (includes v2 cookies like sb-access-token-v2)
  - Prevents retrying the same invalid refresh token repeatedly

## 7. Invalid-Refresh-Token Cleanup Behavior

**Error Handling in Middleware (lines 64-76):**

```typescript
} catch (error: any) {
  // Handle stale refresh token errors gracefully
  if (error?.message?.includes('refresh_token_not_found') || error?.message?.includes('Refresh Token Not Found')) {
    // Log at info level since this is expected stale session cleanup, not an error
    console.log('[MIDDLEWARE] Stale refresh token detected, clearing auth cookies')
    handledRefreshTokenError = true
    // Clear all Supabase auth cookies (including v2)
    const authCookieNames = req.cookies.getAll()
      .map(c => c.name)
      .filter(name => name.startsWith('sb-'))
    authCookieNames.forEach(name => {
      res.cookies.delete(name)
    })
  } else {
    console.error('[MIDDLEWARE] Session check error:', error)
  }
}
```

**Behavior:**
1. **Detect Error:** Checks if error message contains `refresh_token_not_found` or `Refresh Token Not Found`
2. **Log Level:** Uses `console.log` (info) instead of `console.error` since this is expected cleanup
3. **Clear Cookies:** Deletes all cookies starting with `sb-` (clears all Supabase auth cookie variants)
4. **No Retry:** The request-scoped flag `handledRefreshTokenError` prevents duplicate error logs for the same request
5. **Unrelated Cookies Preserved:** Only deletes Supabase auth cookies, leaves other cookies intact
6. **Session State:** Treats the stale session as unauthenticated (user = null)
7. **Routing:** Unauthenticated users are redirected to sign-in for protected routes, allowed for public routes

**Classification of Auth Outcomes:**
- ✅ Valid authenticated session → Continue normally
- ✅ Expected unauthenticated request → Continue normally (public routes)
- ✅ Expired/stale session successfully refreshed → Continue with refreshed cookies
- ✅ Invalid/missing refresh token → Clear cookies, treat as unauthenticated
- ✅ Network/provider failure → Log as error, preserve existing session if possible
- ❌ Unexpected auth failure → Log as error

## 8. Duplicate-Refresh Prevention

**Cause of Duplicate Errors:**
The duplicate `refresh_token_not_found` errors were caused by:
1. First request (homepage): Session refresh attempted but `setAll` was a no-op, so refreshed cookies were lost
2. Second request (navigation/API): Tried to use stale refresh token, which was already consumed in first refresh

**Prevention Mechanisms:**

**1. Proper Cookie Persistence (Primary Fix):**
- Fixed no-op `setAll` in all locations
- Refreshed cookies now persist correctly
- No more stale refresh tokens in browser
- Eliminates the root cause of duplicate errors

**2. Request-Scoped Flag (Secondary Protection):**
```typescript
let handledRefreshTokenError = false
```
- Set to true when first `refresh_token_not_found` error is handled
- Prevents duplicate error logs for the same request
- Prevents duplicate cookie clearing operations

**3. Comprehensive Cookie Clearing:**
- Clears ALL Supabase auth cookies (not just specific ones)
- Ensures no partial state remains
- Prevents partial session state from causing confusion

**4. No Multiple Refresh Attempts:**
- Middleware creates Supabase client once per request
- Only one `getUser()` call in middleware
- No explicit `refreshSession()` calls (relies on automatic refresh)
- Server Components rely on middleware for refresh, avoiding duplicate refreshes

**5. Middleware Scope:**
- Middleware matcher excludes static assets and irrelevant paths
- Does not run on `/api/twilio/*` (uses signature validation)
- Does not run on `/.well-known` (Apple AASA)
- Does not run on `/privacy`, `/terms`, `/compliance` (public pages)
- Reduces unnecessary session checks
